Schedule publication inserts one outbox intent per distinct assigned recipient in the same transaction that marks the schedule published. The stable tenant/schedule/revision/recipient dedupe key prevents request retries from creating duplicate feed entries while a corrected republish receives a new identity. The API attempts delivery only after commit; when schedule email is enabled it uses the outbox ID as the Resend idempotency identity and marks the intent delivered only after provider acceptance or an intentional suppression/non-addressable skip. The lifecycle sweeper recovers pending or expired-lease rows after a crash. `FAILED` rows retry with bounded exponential backoff, while `DEAD_LETTERED` rows erase title, body, and lastError; fixed allowlisted identifier-free logs and metrics provide operator diagnostics.

Delivery prepares the existing global email-suppression read before taking ordered Tenant/User SHARE NOWAIT and outbox UPDATE NOWAIT locks. Current recipient, exact attempt/lease, and database UTC clock checks protect durable feed effects and the new email handoff. Contention postpones without spending failure budget; claim attempts remain strictly increasing. A separate durable failureCount increments only for same-owned failed delivery bookkeeping. Historical rows conservatively consume prior claim budget, excluding the currently unfinished PROCESSING claim. A valid email failure commits the in-app feed with bounded retry bookkeeping, preserving existing read markers. One aborting provider deadline covers preparation and handoff; same-owned database bookkeeping has finite additional headroom.

Global same-address cross-tenant suppression concurrency remains unqualified; the prepared read preserves existing suppression semantics and the locked recipient is checked again. Provider acceptance followed by lost acknowledgement or database commit remains an ambiguous outcome using the stable idempotency identity. Redis fan-out stays best effort after commit; it is neither guaranteed delivery nor a current-recipient lifecycle barrier. Local controlled tests do not qualify PostgreSQL locks, RLS, provider abort behavior, or native operation.

The failure-budget pre migration runs before Prisma schema sync: it no-ops on a fresh missing table, backfills only unknown NULL historical counters, then sets default0/nonNULL. The forward migration validates the bounded check after schema sync without adding or resetting counters. Ledger-owned transactional application, drained legacy workers, and a matching schema-generated Prisma client require reviewed rollout on an admitted private target before this source is enabled. No migration application or client generation is part of the local source tests.
