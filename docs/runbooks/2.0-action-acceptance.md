# LunchLineup 2.0 action acceptance

The [action plan](2.0-action-acceptance.json) gives each current application operation a separate acceptance contract. It also records routes outside the browser catalog, provider deliveries, background work, frontend interactions and operational gates. Every action is pending. The original [84 workflows](2.0-workflow-acceptance.md) and the current selected browser manifests remain required minimums; the complete system includes additional actions.

Each action records its actual source owner, actor boundary, expected success and failure behavior, independent readback, required evidence and proposed scenarios. An optional executable reference identifies a literal test declaration in the current source. That reference does not establish that its assertions cover the contract, that CI selects it, or that it has passed. A scenario without an executable reference is an explicit preparation gap. A shared test can support several contracts only after reviewers verify each relevant assertion and the executed fixture.

Run the source inventory check from an owned local checkout:

```sh
node scripts/verify-action-acceptance.mjs docs/runbooks/2.0-action-acceptance.json .
node --test --test-concurrency=1 scripts/verify-action-acceptance.test.mjs
```

The first command reads and parses source without importing application modules, starting services or contacting infrastructure. It checks catalog identity and owners, literal API-v2 registrations, source anchors, literal test targets and the reviewed browser selections. Its output always says `acceptanceExecuted: false` and `releaseQualified: false`. It reports unmapped workflow rows and missing executable targets as gaps. Its route scanner covers literal `app`/`metricsApp` declarations and the closed application catalog; other registration styles and non-API-v2 ingress require explicit review. Source parsing cannot prove deployed routing, authorization, database isolation or runtime behavior.

Before executing any native scenario, reconcile the infrastructure owner's protected controller/profile, signing and artifact custody receipts and obtain a fresh exclusive QA lease bound to the exact reviewed candidate. A historical source-publication receipt does not authorize a new source ref, CI policy enablement or native run. Use an approved isolated target and a single environment owner. VM107 remains held. VM4014 and VM106 must remain untouched, including probes. This document authorizes no launch, image build, deployment, provider action or production cutover.

For every scenario, retain evidence that binds:

- The source SHA/tree, service image digests, schema/migration state, fixture version and run identity.
- The actual actor, tenant, target, grant/session/policy state and expected denial boundaries. Include self-service, platform, recovery and unauthenticated exceptions specified by the owner.
- A first-attempt terminal result, actual selected case identity and independently read persisted state. A HTTP success or UI message alone does not prove the effect. Interrupted, skipped, retried, mixed-candidate and mocked results retain their narrower scope.
- Failure, stale state, cross-tenant requests, lost responses and replay behavior appropriate to the operation. Do not assume an idempotency guarantee that the implementation does not provide.
- Provider authentication/delivery/readback when required, crash/recovery and cleanup results, and private immutable evidence with checksums. Keep credentials, session capabilities and customer data out of the tracked plan.

Browser qualification must cover the current action contracts as well as every selected baseline case. It needs real API and durable readbacks on one coherent candidate, supported desktop/mobile sizes, Firefox/WebKit, keyboard and accessibility behavior, physical touch devices and unfamiliar-human task completion. Emulation and local mocked component tests are separate evidence. Expand reviewed selections when new acceptance scenarios are implemented; adding a JSON contract does not add a runnable browser case.

Every exposed provider action remains required. Obtain owner-approved sandbox identities and custody for email, OIDC/challenges, billing, payroll, webhooks and durable objects, then verify delivery, denial, replay, outages and recovery. Feature exclusion requires an explicit user scope change and is not a pass.

Operational qualification additionally requires realistic authenticated load and capacity checks, complete current security/dependency/build-network/DAST evidence, genuine backup restore/PITR, migration and old-code/new-schema/rollback drills, alerting and recovery, and months of actual isolated operational testing. Preserve candidate/version history throughout that period. A source fixture, short smoke test or estimated telemetry interval cannot substitute for elapsed operational evidence.

The October 4 source review adds explicit cross-schedule publication replay, payroll export preparation, current payroll authority after waits, notification attempt/lifecycle ownership, terminal diagnostic erasure, and header read-state scenarios. Controlled hook tests exercise actual handlers with a modeled hook ledger and transport; they do not establish React scheduling, browser behavior, database isolation, or external delivery. The payroll transaction authority and outbox ordering findings remain separate repair and native-verification gates. Preserve valid domain replay, immutable payroll snapshots, independent approval, and terminal privacy erasure while addressing them.

The plan and inventory checker are preparation tools. Production readiness requires independently reviewed results for the full objective and a later authorized release decision.
