## Entry and execution boundary

The current approved execution target is VM218 custom-ci: one owner and one job at a time, controller-issued run IDs, fresh 60 GiB backing-cap and parent checks, 32 GiB aggregate job growth limit, synthetic data, run-private databases/volumes/networks and loopback-only test ports. Dispose of each job's resources through its existing cleanup owner. Keep schedules/secrets disabled. Source changes stay in a fresh scoped worktree; every run binds the exact source/tree, dependency lock, pipeline and built image IDs. The development pipeline performs no release signing or publication. Restore its execution policy to the recorded prior state after the controlled run.

Before application runtime, the development pipeline must pass a real Chromium isolation canary using synthetic loopback servers. It checks redirects, custom routes, independent browser/API contexts and rejected proxy overrides; denied targets must receive zero requests and zero TCP connections. A worker-owned loopback proxy on an ephemeral port permits only the fixed `127.0.0.1:8080` upstream. Playwright's HTTP fetch transport requires CONNECT; only the exact `127.0.0.1:8080` authority is accepted, with a literal fixed upstream connection and bounded connection/cleanup. The canary requires positive approved CONNECT evidence from guarded page and API requests. All other CONNECT authorities are rejected. Temporary canary and proxy ports are recorded in retained run receipts and closed by their harness owner; they are not persistent application routes. Service workers, WebSockets and caller overrides of browser networking are rejected.

Runtime services use fresh job-private internal Netavark networks. Before startup, verify network identities, backend, store and isolation settings; after early API startup and before browser fixtures, verify actual container attachments and routes. Disable synthetic-fixture email delivery and keep public URLs on loopback. These controls qualify the selected runtime/browser boundary only. Dependency installation, image pulls and builds still have unqualified network access; synthetic provider keys do not enforce isolation, and source inspection cannot certify zero external traffic during earlier attempts. Complete separate build-network and broader security qualification before any release.

VM218 disposable jobs can provide repeated regression evidence. They do not prove a continuously running multi-month service or preserved application state between jobs. A persistent isolated soak target needs a separately accepted owner/storage/backup/resource contract before it is created; it cannot use VM4014, VM106, the held VM107 or shared unbounded storage. No such target is approved by this document.
